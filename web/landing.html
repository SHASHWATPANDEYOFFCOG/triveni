The problem

One credit lands. Nobody can say what it is made of.

A payment gateway does not settle transaction by transaction. It nets a day's payments, subtracts its fees, and sends a single credit. The bank statement shows one line. The ledger expects hundreds. Somebody has to reconcile that by hand, every day, and explain the difference.

What the bank shows you
NEFT CR · RAZORPAY SOFTWARE PVT —

One line. No transaction ids, no fee breakdown, no GST split, no TDS. Reconciling it means matching that single figure back to hundreds of payments whose sum it is not — because fees came out in between.

The solution

One spine. Three loops.

Not three products bolted together — one reconciliation result, read three ways. Every loop shares the same money arithmetic, the same audit log and the same refusal to move a rupee.

Close

Reconcile

Three-way matching across payments, bank and ledger. Deterministic keys first, then blocking, then Fellegi–Sunter, then a global assignment that solves the whole day at once instead of greedily.

Explain

Decompose

Every netted settlement broken into gross, MDR, GST-on-fee, TDS and refunds — with the rates fitted by robust NNLS from your own data, not hard-coded. Ask it questions in English; it answers only from rows it can cite.

Foresee

Forecast

Settlement-aware cash forecasting on the Indian bank calendar, with conformal prediction intervals per horizon step. Scored on MASE and pinball loss against a seasonal-naive baseline — never MAPE.

How it works

Six stages. The model appears in exactly one of them.

Each stage consumes what the previous one could not match, so the expensive techniques only ever see the rows the cheap ones failed on. The ladder is the reason a language model touches so few rows.

  1. 1 Deterministic keysUTR and RRN. Exact, free, and correct by construction. no model
  2. 2 BlockingCandidate generation, scored on pair completeness and reduction ratio. no model
  3. 3 Fellegi–Sunter linkageProbabilistic record linkage with m and u fitted by EM. no model
  4. 4 Global assignmentHungarian matching plus CP-SAT subset-sum for netted bundles. Proven optimal, not greedy. no model
  5. 5 Settlement decompositionFee algebra with rates fitted by robust NNLS. GST on the fee, never on the sale. no model
  6. 6 ResidueOnly what nothing above could resolve. Free text is classified into a closed enum and one sentence is written. —
AI judgment

Use a model for language. Use mathematics for money.

The interesting engineering decision in this project is where the model is not. Matching, fees, thresholds and allocation are optimisation and statistics, because they have to be reproducible, auditable and provably optimal. A language model is used where language is the actual problem.

Where a model is and is not used, with the file that proves it
DecisionModel?What is used instead, and whyProof
Matching a payment to a bank line No Hungarian assignment with a priced no-match column, so declining is a modelled option rather than a fallback. recon/assign.py
Splitting a netted settlement No Meet-in-the-middle and CP-SAT subset-sum. Integer paise, so equality is exact. recon/subsetsum.py
Fee, GST and TDS rates No Robust non-negative least squares fitted from the data. A hallucinated basis point is a real loss. recon/fees.py
The auto-post threshold No Split conformal prediction with the finite-sample correction, so the bound is a bound rather than an average. core/conformal.py
Reading a messy bank narration Yes Free text is genuinely a language problem. Output is parsed into a closed enum; anything else abstains. recon/escalate.py
Answering a question in English Yes The model selects among hand-written SQL templates. It never generates SQL, and every numeral is checked against the rows returned. qa/compile.py
◈ Switch the model off entirely with TRIVENI_LLM_MODE=off and matching is unchanged. The books still close; the rows that needed language abstain into typed exceptions for a human. That is the test of whether a system's intelligence is load-bearing or decorative.

Who it is for

The part still done by hand.

The finance team closing a month

Three-way reconciliation with an error bound they can quote to an auditor, and an append-only log that proves what was decided and when.

The founder asking where the money went

"Why is this settlement short?" answered in English, from rows it can cite — and refused outright when the data cannot support an answer.

The operator planning payroll

Cash forecast on the real bank calendar, including the second and fourth Saturday, with intervals that state their own coverage honestly.

Architecture

A spine, not a pile of scripts.

Money is integer paise everywhere; a lint fails the build if a float touches the money path. Time is an injectable clock. Every identifier is a canonical JSON digest, which is also what the Merkle leaves are built from.

web/zero-build ES modules · no npm, no bundler, no webfont
api/FastAPI · 14 read/propose routes · SSE for the close · an MCP server
recon/the six-stage ladder · assignment, subset-sum, fee algebra
forecast/model ladder · rolling-origin backtest · conformal intervals
qa/template-constrained NL→SQL · numeral grounding
core/money · clock · policy · conformal · Merkle audit · the LLM gateway
⚠ Triveni never calls a write tool. The Razorpay adapter's allowlist contains ten literal read tools, with an import-time assertion that the eleven write tools never appear in it, and a test that asserts they are unreachable. ActionClass.MOVE_MONEY is refused unconditionally — there is no configuration that enables it.
